# Protocol RFC process

Use an RFC for receipt fields, authority states, policy semantics, verification rules, adapter contracts, or compatibility changes. Ordinary defects use a bug report; suspected vulnerabilities use a private advisory.

An RFC must state the observed problem, affected actors, current evidence, proposed semantics, rejected alternatives, privacy and abuse risks, compatibility impact, migration path, and regression fixtures. Name dissent and unresolved questions rather than manufacturing consensus.

Maintainers label an RFC `discussion`, `accepted`, `rejected`, or `superseded`. Acceptance requires an explicit decision record and tests. Institutional feedback is technical evidence, never implied approval. Genuine DDEX standards gaps may be submitted through DDEX's own change process separately from product promotion.
